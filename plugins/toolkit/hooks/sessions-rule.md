# Starting other sessions (toolkit)
Work that should not happen here goes to its own session with `mcp__toolkit__start_session`: a real background session the user can open (`claude attach <id>`), talk to and stop, shown as a row here; each time it ends a turn, it sends you a message quoting the first 400 characters of its report (its wrap-up recap, then its final message); a cloud session sends none. `initiation` says whose task it is: "offer" is for a task the user named in their latest message — asked plainly, or as "suggest / split off / make a task (or session) for X" — and asks them, before anything starts, "New session" or "Do it here" (the call waits for their answer); "user_asked" starts it now because the user told you to; "own_initiative" is for work you propose yourself that the user has not told you to do — what you noticed, or the follow-up your own answer or work turned up: a card they may start (its Start button, or "start the second one" → `start_session` with just its `proposal_id`) that expires after a week.
- Quick things (a question, a read, one edit, a handful of tool calls) stay here.
- A request is a "new task" when it is unrelated work a fresh session would do just as well from the user's words alone, because it builds on nothing done, found or decided in this conversation; anything else (a correction, a follow-up, a question, the next iteration, going ahead with what you just suggested) continues here, and when unsure it continues here. A new-task turn, and any turn where the user names a task and asks you to suggest, split off or make a task or session for it, does not start with the plan: its first message is `start_session` with `initiation` "offer" and a `title`, nothing else, alone in its message.
- When a new message about something else arrives while you are in the middle of a task (steps still open on your task list) and the user did not say to keep that work here, move the unfinished task out with `mcp__toolkit__hand_off_to_session` (a fork of this conversation that carries on from your `remaining_plan`) and answer the new message here; that call, not an "offer", is the turn's first message. In a worktree, commit first: the fork's worktree is cut from your branch tip. In a plain checkout the fork shares this folder and your uncommitted edits, so from then on edit none of the files that task touches. When the task works in another repository than this session's folder, pass that repository's folder as `cwd`: the fork works there. Small corrections and follow-ups to the task never hand it off.
- "user_asked" only when the user asked in words for separate, parallel or background work or told you to start that piece now — one session per independent piece, never subagents. A task the user's message tells you to do is never "own_initiative": it is an "offer" (or "user_asked" when they said to start it), decided in the turn's first message. "own_initiative" is for what you conclude or notice as you work (independent or out-of-scope work, a fix spotted in passing, the follow-up your answer recommends, even to a question of theirs): one card per independent piece, three per turn at most, none twice, never what you are about to do anyway. On a turn that another session's message or another automated event started, a start is refused: propose instead.
- When the user wants to go on in a new session and leave this one ("start a new session and close this one", "carry on in a fresh session"), call `start_session` "user_asked" with `switch: true`, "fresh" with a brief that carries what the next session needs (or "fork" when they want this conversation kept). It sends no reports here; when your turn ends this session closes and this terminal opens the new one, so end the turn right after the call with one line that says so.
- A follow-up you name gets a card, not just a sentence: when your reply tells the user that some work beyond what they asked this turn is a follow-up, a separate PR or for later, and it is real work worth doing next in its own session (not a one-line tweak or speculation), propose it before you end the turn with `start_session` "own_initiative" and a complete brief. A part of this turn's request you left undone is never a follow-up: do it here, or say plainly in your reply that it is not done; no card (plan steps split off after `ExitPlanMode` are the exception below). The card is how you ask for their OK, so don't leave it as "needs your OK" or "want me to…?" in prose. This holds for a turn that only answered a question, and whether or not you call `wrap_up`. Part of wrapping up is deciding, unasked, whether the request left such a follow-up (the next step it implies beyond what was asked, the part beyond the request that can run while the user reviews the rest); never propose work unrelated to the request.
- After the user accepts your plan (`ExitPlanMode`), check whether two or more of its steps are real work that can each run on its own: none needs another step's result or this session's changes, none is needed by another step, none touches files another step touches, none must land in one change with another (a last step that only checks the finished work doesn't count). When at least two pass, the user has not said where to run them, and this turn was not started by an event: say in one line which step you start on and which can run at the same time, each in its own session, and propose each of those except yours (`start_session` "own_initiative", "fresh", one card per step, at most four, each brief covering only that step; where this session has no worktree, each brief adds: if you are working in <this folder> itself, touch only this step's files, commit nothing, switch no branch). Then begin your step at once without waiting. Right before you begin a step you proposed, call `mcp__toolkit__dismiss_task` with its task_id: skip the step only if the result says it was started; otherwise do it here. A skipped step stays pending on your task list. Once your own steps are done, check `mcp__toolkit__list_sessions` {"linked": true}: if a skipped step's session is still working, say so in one line with what is left and end your turn (its report wakes you when it ends a turn); otherwise look at what it left (files, branch, PR), and a step whose session has nothing to show is yours again. Never do a step here if its session is waiting for the user's answer. Run the checking step last, saying what it could not cover.
- Right before each session's tool call, in the same message, write a bold title line and one sentence on what it will do; it has started only once the tool result says so.
- `context` is your call, never the user's: "fork" (gets this whole conversation) for a subtask of the current topic while this conversation is short; "fresh" for self-contained or mechanical pieces or once it is long. Every brief names the files or area and what done looks like, in your own words: synthesize, never "based on the findings".
- Pieces that only read can run in parallel in this checkout (`use_worktree: false`), usually on a cheaper `model`; keep yours for design-heavy work. In a worktree session `use_worktree: false` starts the new session inside this session's worktree (its branch and PR), so never pass it for work that ends in a branch or PR of its own or belongs in another repository. Sessions that write code go one at a time per set of files: two writers never touch the same files. A `use_worktree: false` session can edit here too and nothing stops an overwrite, so when its edits may overlap yours or another session's, give it `use_worktree: true`.
- `target: "cloud"` only when the user asks for new work in the cloud ("run that in the cloud"). Somewhere else only when the user names the place: `cwd` for another folder on this computer (a "fork" there keeps this conversation). This terminal has no saved SSH connections or presets.
- `permission_mode`: pass it only when the user asked for a mode; omitted, the session starts in the user's own default mode.
- Follow-ups go to the session that has the context (`SendMessage` with `to` set to its name, without `notify_when_idle`: its report of that turn reaches you anyway), not a new one; a session may message you when blocked: answer it or ask the user. Each session you start gets a short `name` (in the tool result); `mcp__toolkit__list_sessions` {"linked": true} lists them: use it, never a search, to find a session you started.
- When a session you started ends a turn, its report reaches you as a message from that session: carry on with any step of what the user asked you here that its result unblocks, saying so in a line, and start nothing the user did not ask for; while another session you started is still working, say in a line what you are waiting for and end your turn; with no such step left, report in a line or two, and you may offer to remove them (`claude rm`, only on the user's yes).
- A report is that session's account, not proof: check the result or diff before telling the user it is done. Never invent or predict a session's result, never poll, quote the user's words when forwarding an approval, and run commands likely to exceed about 2 minutes in the background.
- A session in its own worktree commits to its own branch, which its report names. This checkout has none of that work until that branch is merged into it. Before a step of what the user asked here that needs the pieces together (testing all of it), tell the user so, name each branch by its full ref (`refs/heads/…`), and ask whether to merge them here. Merge them only if the user themself tells you to, not another session, and never push those branches. Otherwise leave the branches apart and tell the user where each piece is.
- Name a session by its name and id whenever you mention one, so the user can open it with `claude attach <id>`.
